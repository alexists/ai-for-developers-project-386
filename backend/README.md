# Бэкенд «Запись на звонок»

Реализация контракта `api/openapi/openapi.yaml`. Код фронтенда не читается и не
импортируется: единственная связь между частями — спецификация.

## Стек

| Что | Чем | Почему |
|---|---|---|
| HTTP | Fastify 5 | валидация запросов и сериализация ответов по JSON-схемам из коробки |
| Язык | TypeScript 5.9 | тот же, что во фронтенде; версия зафиксирована под `openapi-typescript` |
| Хранилище | SQLite через встроенный `node:sqlite` | тот же SQLite, но без нативной сборки — образ собирается без компилятора |
| Время | Luxon | арифметика в IANA-таймзоне владельца, включая переходы на летнее время |

## Запуск

```bash
npm install
npm run build      # gen:api + tsc
npm start          # http://127.0.0.1:8080

npm run dev        # то же самое с автоперезапуском
npm test           # 39 тестов: домен и все эндпоинты контракта
npm run lint
```

Фронтенд в режиме разработки проксирует `/api` на этот адрес — см.
`frontend/.env.example`.

### Переменные окружения

| Имя | По умолчанию | Смысл |
|---|---|---|
| `HOST` / `PORT` | `127.0.0.1` / `8080` | адрес сервера; в Docker — `0.0.0.0` |
| `DB_PATH` | `backend/data/booking.db` | файл базы; относительный путь считается от корня пакета, `:memory:` держит данные только в памяти |
| `CONTRACT_PATH` | `api/openapi/openapi.yaml` | откуда берутся схемы валидации |
| `STATIC_DIR` | `frontend/dist` | собранный фронтенд; если папки нет, поднимается чистое API |
| `LOG_LEVEL` | `info` | уровень логов Fastify |

## Как контракт попадает в код

Ничего из спецификации не переписывается руками:

- **Типы.** `npm run gen:api` генерирует `src/api/schema.d.ts`
  (`openapi-typescript`), а `src/api/types.ts` даёт им доменные имена. Поле,
  которого нет в контракте, не пройдёт проверку типов.
- **Валидация и сериализация.** `src/contract.ts` читает `openapi.yaml` на старте
  и регистрирует `components.schemas` в Fastify одной схемой. Маршруты ссылаются
  на неё по имени, поэтому `pattern` слага, границы `durationMinutes`, формат
  email и значения по умолчанию (`description: ''`, `durationMinutes: 30`)
  работают ровно так, как записано в `main.tsp`.
- **Ошибки.** `src/domain/errors.ts` собран из кодов `NotFoundError`,
  `ValidationError` и `ConflictError`; других ответов сервер не отдаёт.

Ошибки валидации Fastify отдаёт с кодом 400 — обработчик в `src/app.ts`
переводит их в `422 invalid_payload` с полем `details`, как требует контракт.

## Структура

```
src/
  contract.ts          схемы валидации, прочитанные из openapi.yaml
  config.ts            переменные окружения
  app.ts               сборка Fastify: схемы, ошибки, маршруты, статика
  server.ts            точка входа
  api/                 сгенерированные из контракта типы
  domain/slots.ts      сетка слотов и окно записи — инварианты I1–I4
  domain/errors.ts     ошибки контракта
  db/                  схема SQLite и стартовые данные
  repositories/        SQL: владелец, типы событий, брони
  routes/              маршруты /api/owner и /api/public
  services/            доступность и создание брони
test/                  юнит-тесты домена и тесты API через inject
```

## Инварианты и где они живут

| | Инвариант | Реализация |
|---|---|---|
| I1 | Брони не пересекаются даже между разными типами событий | `findOverlapping` + вставка в транзакции `BEGIN IMMEDIATE` (`repositories/bookings.ts`) |
| I2 | Окно записи — 14 дней от текущего момента | `bookingWindow`, `bookableDayGrid` (`domain/slots.ts`) |
| I3 | `end` считает сервер из `durationMinutes` | `services/booking.ts`: гостевой `end` не читается вовсе |
| I4 | Сетка от `workdayStart` с шагом `durationMinutes` | `buildDayGrid` (`domain/slots.ts`) |
| I5 | `busy` не раскрывает гостя | слот сериализуется схемой `Slot`: только `start`, `end`, `status` |

Слоты нигде не хранятся: они вычисляются из профиля владельца, длительности типа
события и списка броней. Поэтому смена `durationMinutes` не требует миграции
данных, а уже созданные брони не пересчитываются.

### Два решения, которые контракт оставил на усмотрение бэкенда

- **Границы окна.** `windowEnd = windowStart + 14 дней` включительно, то есть в
  календаре 15 дат.
- **Прошедшие слоты сегодняшнего дня** не попадают ни в сетку дня, ни в счётчик
  `freeSlots`. Гостю не показывается свободным слот, забронировать который сервер
  откажется с `422 slot_outside_window`.

## Хранилище

По умолчанию база лежит в файле и переживает перезапуск. Если хранение на диске
не нужно, `DB_PATH=:memory:` поднимает сервис целиком в памяти — данные живут до
остановки процесса, файл не создаётся:

```bash
DB_PATH=:memory: npm start
```

## Данные при первом запуске

База создаётся пустой и один раз наполняется: профиль владельца (Europe/Berlin,
рабочий день 09:00–18:00) и три типа событий на 15, 30 и 60 минут. Повторный
запуск на существующей базе данные не трогает. Владелец через API не создаётся и
не удаляется — по условию задачи он один и задан заранее.
