# Проект: «Запись на звонок»

Упрощённый аналог Cal.com. Без авторизации: один владелец календаря, гости
бронируют анонимно. Приложение должно собираться в Docker-образ.

## Подход

Design First. `api/main.tsp` — единственный источник правды. Фронтенд и бэкенд
реализуются по сгенерированному `api/openapi/openapi.yaml` и не читают код друг друга.

## Железные правила

- Не менять поведение API в обход спецификации. Нужен новый эндпоинт или поле —
  сначала правим `main.tsp`, компилируем, потом реализуем.
- После правки `main.tsp` всегда запускать `npx tsp compile .` и коммитить
  обновлённый `openapi.yaml` вместе с ним.
- Клиент для фронтенда и модели для бэкенда генерировать из OpenAPI, не писать руками.
- Не писать код вне текущей задачи. Не создавать «на будущее» абстракции,
  эндпоинты и поля, которых нет в спецификации.

## Инварианты бронирования

1. Бронирования не пересекаются по времени между собой — даже для разных типов
   событий. Календарь у владельца один.
2. Окно записи — 14 дней от текущего момента.
3. Длительность брони равна `durationMinutes` типа события; `end` считает сервер.
4. Сетка слотов строится от начала рабочего дня владельца с шагом, равным
   длительности типа события.
5. Все моменты времени в API — UTC.

## Команды

```bash
cd api && npx tsp compile .     # сгенерировать OpenAPI
```

## Сценарии для проверки

Список того, что приложение обязано уметь, — в `scenarios.md`. Это приёмочные
критерии: у каждого сценария указано, каким тестом он закрыт. Меняешь поведение —
сначала правь сценарий, потом код и тест.

## Формат коммитов

[Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/). По ним
release-please собирает CHANGELOG и считает следующую версию, поэтому формат
обязателен — в том числе для коммитов, которые делает агент.

```
<тип>(<область>): что сделано

<тело: зачем, если из заголовка не очевидно>
```

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`.
Области: `api`, `backend`, `frontend`, `e2e`, `docker`, `ci`.

- `feat` поднимает минорную версию, `fix` — патч; остальные типы версию не двигают.
- Ломающее изменение API — `!` после типа и абзац `BREAKING CHANGE:` в теле.
- Заголовок — в повелительном наклонении, до 72 символов, без точки в конце.
- Правка `main.tsp` вместе с пересобранным `openapi.yaml` — это `feat(api):`
  или `fix(api):`, смотря что поменялось в поведении.

Формат проверяется в CI (job «Формат коммитов» в `ci.yml`) на каждом pull request.

В changelog попадают все типы, включая `ci` и `chore`: флаг `hidden` в
`release-please-config.json` ничего не скрывает, потому что его применяет
`filterCommits`, а тот вызывается только стратегиями `node`, `python` и
`java-yoshi-mono-repo`. У нас `release-type: simple`. Поэтому у каждого типа
должно быть имя раздела — иначе release-please выведет сырое `ci`.

## Проверки перед коммитом

```bash
cd backend  && npm run build && npm run lint && npm test
cd frontend && npm run lint && npm run build
cd e2e      && npm run build:app && npm test
```
