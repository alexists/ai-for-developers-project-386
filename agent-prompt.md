# Промпт для Claude Code

Запускайте в пустом репозитории. Сначала `/plan` (Shift+Tab дважды) — пусть агент
покажет план и структуру файлов, и только потом разрешайте писать.

---

Подготовь TypeSpec-спецификацию API для сервиса «Запись на звонок» — упрощённого
аналога Cal.com. Спецификация будет единственным источником правды: по ней фронтенд
и бэкенд реализуются независимо. Код приложения писать не нужно, только контракт.

## Домен

**Владелец календаря** — один заранее заданный профиль. Регистрации и авторизации
нет: админская часть всегда работает от его имени, гость работает анонимно.
Поля: имя, описание, аватар, таймзона, начало и конец рабочего дня.

**Тип события** — шаблон встречи: `id` (слаг, задаёт владелец), `title`,
`description`, `durationMinutes` (по умолчанию 30).

**Слот** — вычисляемая сущность, в БД не хранится. Интервал
`[start, start + durationMinutes)` на сетке, построенной от начала рабочего дня
владельца с шагом, равным длительности типа события. У слота есть статус
`free` или `busy`.

**Бронирование** — запись гостя на слот: `id`, ссылка на тип события,
скопированное название типа, `start`, `end`, контакты гостя
(`name`, `email`, необязательные `notes`), `createdAt`.

## Правила

1. Два бронирования не могут пересекаться по времени, даже если относятся к разным
   типам событий: календарь у владельца один. Слот 15-минутного типа становится
   `busy`, если его перекрывает встреча 30-минутного типа.
2. Окно записи — 14 дней от текущего момента. День или слот вне окна недоступен.
3. Длительность бронирования равна длительности типа события: гость передаёт только
   `start`, `end` вычисляет сервер.
4. Занятый слот показывается гостю как `busy`, но не раскрывает, кто его занял и на
   какой тип события.
5. Все моменты времени в API — UTC (`utcDateTime`). Даты календаря и рабочие часы —
   `plainDate` / `plainTime` в таймзоне владельца.

## Экраны, которые контракт должен обслуживать

1. **Лендинг** — статика, API не нужен.
2. **Каталог** — профиль владельца в шапке + карточки типов событий
   (название, описание, длительность).
3. **Страница бронирования** — три колонки:
   - карточка выбранного типа события и сводка выбора;
   - месячный календарь, где у каждого дня окна подписано количество свободных
     слотов, а дни вне окна некликабельны;
   - панель «Статус слотов» за выбранный день: список интервалов со статусом
     «Свободно» / «Занято».
4. **Форма гостя и подтверждение** — создание брони и просмотр её по id.
5. **Админка** — управление типами встреч и единый список предстоящих встреч по
   всем типам с фильтрами по датам.

Обрати внимание: для календаря и для панели слотов нужны разные эндпоинты. Календарю
нужна агрегированная сводка по дням на всё окно, панели — детальная сетка одного дня.
Отдавать полную сетку за 14 дней ради подписей в календаре расточительно.

## Требования к спецификации

- TypeSpec, точка входа `main.tsp`, эмиттер `@typespec/openapi3`.
- Разделить пространства имён: `/api/owner` и `/api/public`. Публичные модели не
  должны раскрывать внутренние поля.
- Ошибки — отдельные модели с `@statusCode` и машиночитаемым `code`:
  404 (не найдено), 409 (`slot_taken`, занятый id типа события),
  422 (слот вне окна, слот не на сетке, невалидные данные).
- Валидация на моделях: `@pattern` для слага, `@minLength`/`@maxLength`,
  `@minValue`/`@maxValue` для длительности, `@format("email")`.
- Каждая операция и каждое нетривиальное поле — с doc-комментарием `/** */`.
- `npx tsp compile .` проходит без ошибок и предупреждений.

## Результат

- `main.tsp`, `tspconfig.yaml`;
- сгенерированный `openapi/openapi.yaml`;
- в README — таблица «экран → эндпоинт» и список инвариантов бронирования.

После генерации проверь спецификацию по чеклисту и сообщи, что не покрыто:
каждый экран из списка выше должен собираться из существующих эндпоинтов без
дополнительных запросов «на клиенте».
