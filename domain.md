# Доменная модель

## Владелец календаря (Owner)

Единственный заранее заданный профиль. Регистрации, входа и личных кабинетов нет:
всё, что лежит под `/api/owner`, работает от его имени. Профиль создаётся при
инициализации приложения и не может быть создан или удалён через API.

| Поле | Тип | Смысл |
|---|---|---|
| `name` | string | Имя в шапке публичных страниц |
| `bio` | string? | Короткое приветствие для гостя |
| `avatarUrl` | url? | Аватар; если пусто — плейсхолдер на фронтенде |
| `timeZone` | string | IANA-таймзона, в которой трактуются даты и рабочие часы |
| `workdayStart` / `workdayEnd` | plainTime | Границы рабочего дня — из них строится сетка слотов |

Рабочие часы в условии задачи не заданы. Без них сетку пришлось бы строить
круглосуточно, поэтому они вынесены в профиль как явный параметр.

## Тип события (EventType)

Шаблон встречи, который владелец публикует для записи. Идентификатор задаёт сам
владелец в виде слага — он попадает в URL страницы бронирования.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | string | Слаг `^[a-z0-9]+(-[a-z0-9]+)*$`, уникален |
| `title` | string | Название на карточке каталога |
| `description` | string | Описание на карточке |
| `durationMinutes` | int32 | Длительность встречи; она же — шаг сетки слотов |

`durationMinutes` играет двойную роль: задаёт и длину брони, и шаг сетки. Поэтому
у типа «15 минут» и типа «30 минут» разные сетки при общей занятости календаря.

## Слот (Slot)

Вычисляемая сущность. **В базе не хранится** и не имеет идентификатора: слот —
это результат наложения трёх вещей на конкретный день:

1. сетка от `workdayStart` с шагом `durationMinutes` до `workdayEnd`;
2. окно записи в 14 дней от текущего момента;
3. существующие бронирования — все, независимо от типа события.

| Поле | Тип | Смысл |
|---|---|---|
| `start` / `end` | utcDateTime | Границы интервала, `end = start + durationMinutes` |
| `status` | `free` \| `busy` | Свободен или перекрыт бронированием |

Альтернатива — пре-генерировать слоты записями в БД — требовала бы
перестраивать таблицу при каждом изменении длительности типа события и при
сдвиге окна записи. Вычисление на лету снимает этот класс рассинхронизаций.

Занятый слот отдаётся гостю как `busy` и не раскрывает ни имени гостя,
ни того, какой тип события его занял.

## Бронирование (Booking)

Факт записи гостя на конкретное время. Единственная сущность, которая реально
хранится и меняет состояние календаря.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | string | Идентификатор, по нему открывается подтверждение |
| `eventTypeId` | string | Ссылка на тип события |
| `eventTypeTitle` | string | Название, скопированное на момент брони |
| `start` / `end` | utcDateTime | Границы встречи; `end` вычисляет сервер |
| `guest` | Guest | `name`, `email`, необязательные `notes` |
| `createdAt` | utcDateTime | Момент создания |

`eventTypeTitle` намеренно денормализован: список встреч владельца остаётся
читаемым, даже если тип события переименовали или удалили, и рисуется одним
запросом без джойнов на клиенте.

Гость передаёт только `start` — `end` сервер выводит из длительности типа
события. Иначе клиент мог бы прислать несогласованную пару.

## Публичный сценарий гостя

Гость работает анонимно, аккаунт не создаётся ни на одном шаге.

1. **Лендинг.** Статическая страница, API не нужен. Кнопка «Записаться» ведёт в каталог.
2. **Каталог.** `GET /api/public/owner` — шапка с именем и аватаром владельца.
   `GET /api/public/event-types` — карточки: название, описание, длительность.
   Гость выбирает карточку.
3. **Календарь.** `GET /api/public/event-types/{id}/availability` — дни окна записи
   с количеством свободных слотов. Дни вне окна и дни без свободных слотов
   некликабельны. Гость выбирает день.
4. **Выбор времени.** `GET /api/public/event-types/{id}/slots?date=...` — сетка дня
   со статусами. Гость видит и занятые интервалы, что даёт представление о
   загруженности, и выбирает свободный.
5. **Форма.** Гость вводит имя, email и при желании заметки.
6. **Создание брони.** `POST /api/public/bookings` с `eventTypeId`, `start` и данными
   гостя. Возможные исходы:
   - `201` — бронь создана;
   - `409 slot_taken` — время заняли, пока гость заполнял форму: фронтенд должен
     перезапросить слоты дня и попросить выбрать заново;
   - `422 slot_outside_window` — слот вышел за окно записи;
   - `422 slot_not_on_grid` — время не совпадает с сеткой;
   - `404 event_type_not_found` — тип события удалили.
7. **Подтверждение.** `GET /api/public/bookings/{id}` — экран с деталями встречи,
   доступный по ссылке.

Шаг 6 — единственный, который меняет состояние. Все предыдущие идемпотентны,
и гость может свободно возвращаться назад.

## Правила занятости

1. Два бронирования не пересекаются по времени, даже если относятся к разным типам
   событий: календарь у владельца один. 30-минутная встреча гасит два
   15-минутных слота.
2. Окно записи — 14 дней от текущего момента. Слот в прошлом или за границей окна
   недоступен.
3. Длительность брони всегда равна `durationMinutes` своего типа события.
4. Сетка строится от `workdayStart` с шагом `durationMinutes`; слот, не влезающий
   целиком до `workdayEnd`, в сетку не попадает.
5. Все моменты времени в API — UTC. Даты календаря и рабочие часы трактуются
   в таймзоне владельца.
