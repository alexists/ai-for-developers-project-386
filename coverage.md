# Проверка покрытия сценариев

Спецификация скомпилирована на TypeSpec 1.15.0: `npx tsp compile .` проходит без
ошибок и предупреждений, генерируется 12 эндпоинтов и 16 схем.

## Сценарии владельца

| Сценарий из задания | Эндпоинт | Статус |
|---|---|---|
| Профиль владельца используется админкой по умолчанию | `GET /api/owner/profile` | ✅ |
| Создаёт тип события: id, название, описание, длительность | `POST /api/owner/event-types` | ✅ |
| Смотрит список своих типов событий | `GET /api/owner/event-types` | ✅ |
| Редактирует тип события | `PATCH /api/owner/event-types/{id}` | ✅ |
| Удаляет тип события | `DELETE /api/owner/event-types/{id}` | ✅ |
| Смотрит предстоящие встречи всех типов в одном списке | `GET /api/owner/bookings` | ✅ |
| Фильтрует список по датам и типу события | query `from`, `to`, `eventTypeId` | ✅ |
| Отменяет встречу | `DELETE /api/owner/bookings/{id}` | ✅ |

## Сценарии гостя

| Сценарий из задания | Эндпоинт | Статус |
|---|---|---|
| Видит страницу с видами брони: название, описание, длительность | `GET /api/public/event-types` | ✅ |
| Видит, чей это календарь | `GET /api/public/owner` | ✅ |
| Открывает календарь на ближайшие 14 дней | `GET /api/public/event-types/{id}/availability` | ✅ |
| Выбирает свободный слот дня | `GET /api/public/event-types/{id}/slots?date=` | ✅ |
| Создаёт бронирование на выбранный слот | `POST /api/public/bookings` | ✅ |
| Открывает подтверждение брони | `GET /api/public/bookings/{id}` | ✅ |
| Не создаёт аккаунт и не входит в систему | эндпоинтов авторизации нет | ✅ |

## Правила из задания

| Правило | Где зафиксировано |
|---|---|
| На одно время нельзя две записи, даже разных типов событий | инвариант I1 в `main.tsp`; `409 slot_taken` при создании; `status: busy` в сетке слотов |
| Слоты формируются на 14 дней от текущей даты | инвариант I2; `windowStart` / `windowEnd` в `AvailabilityCalendar`; `422 slot_outside_window` |
| Гость записывается только на свободный слот из окна | `isBookable` в `DayAvailability`; `status` в `Slot`; `422 slot_not_on_grid` |
| Регистрации и авторизации нет | нет ни одного эндпоинта аутентификации; профиль владельца только читается |

## Экраны из макета

| Экран | Запросы |
|---|---|
| Лендинг | нет, статика |
| Каталог типов событий | `GET /api/public/owner`, `GET /api/public/event-types` |
| Страница бронирования: карточка типа | `GET /api/public/event-types/{id}` |
| Страница бронирования: месячный календарь с подписями «N св.» | `GET /api/public/event-types/{id}/availability` |
| Страница бронирования: панель «Статус слотов» | `GET /api/public/event-types/{id}/slots?date=` |
| Форма гостя и подтверждение | `POST /api/public/bookings`, `GET /api/public/bookings/{id}` |
| Админка: типы встреч | `GET`/`POST`/`PATCH`/`DELETE /api/owner/event-types` |
| Админка: предстоящие записи | `GET /api/owner/bookings` |

Каждый экран собирается из существующих эндпоинтов без дополнительной логики
«склейки» на клиенте.

## Осознанно не вошло в контракт

| Что | Почему |
|---|---|
| Перенос брони | В условии нет. Пересоздание = отмена + новая бронь |
| Отмена брони гостем | В условии нет; отмена доступна владельцу |
| Пагинация списков | Объёмы данных проекта этого не требуют |
| Уведомления на email | Нет в условии, тянет за собой внешнюю зависимость |
| Индивидуальное расписание по дням недели, выходные | В условии нет; рабочие часы одни на все дни |
| Мультипользовательность | В условии явно исключена |

Лишние эндпоинты в контракте — это лишняя работа для обеих частей приложения.
Добавить их позже дешевле, чем выкидывать реализованное.
