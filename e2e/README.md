# Интеграционные сценарии

Проверяют приложение целиком в настоящем браузере: фронтенд, бэкенд и контракт
работают вместе. Моков нет — запросы уходят в реальное API.

Что именно должно работать, описано в [scenarios.md](../scenarios.md); здесь —
как это проверяется.

## Как это запускается

Сценарии гоняются по **собранному** приложению в той же связке, что и в Docker:
один процесс Node отдаёт и `/api`, и статику фронтенда. Так проверяется ровно то,
что уезжает в образ, а не поведение dev-сервера с прокси.

База поднимается в памяти (`DB_PATH=:memory:`), поэтому каждый прогон стартует с
чистого календаря и трёх стартовых типов событий. Сервер запускает сам Playwright
— поднимать ничего заранее не нужно.

```bash
npm install
npx playwright install chromium
npm run build:app        # сборка бэкенда и фронтенда
npm test                 # 9 сценариев, ~27 секунд

npm run test:ui          # интерактивный режим
npm run report           # HTML-отчёт последнего прогона
```

## Сценарии

| Сценарий | Что проверяет |
|---|---|
| Гость проходит бронирование от лендинга до подтверждения | G1. Основной путь: лендинг → каталог → тип события → день окна записи → свободный слот → форма → подтверждение. Детали встречи на экране подтверждения совпадают с введёнными, `end` посчитан сервером, встреча появляется в списке владельца |
| Подтверждение открывается повторно по прямой ссылке | G2. Бронь доступна по сохранённому адресу без авторизации |
| Занятое время закрывается и для другого типа встречи | G3. I1: получасовая консультация гасит перекрытые пятнадцатиминутные слоты «Знакомства». I5: занятый слот не раскрывает имя и почту гостя. Остальные слоты дня остаются доступными |
| Слот, занятый во время заполнения формы, не бронируется | G5. Конкурирующая бронь создаётся запросом, пока форма открыта в браузере: гость остаётся на странице выбора, видит сообщение о конфликте, а сетка перезапрашивается и показывает время занятым |
| Форма не отправляет некорректные данные гостя | G4. Ограничения модели `Guest` из контракта отсекают пустое имя и адрес без домена; запрос не уходит, гость остаётся в форме |
| Новый тип встречи появляется в публичном каталоге | O1. Админка и публичная часть работают с одними данными: созданный тип сразу доступен гостю по своему адресу |
| Правка типа встречи видна гостю | O2. Новые название и описание видны в каталоге, идентификатор неизменяем, новая длительность задаёт новый шаг сетки слотов (I4) |
| Фильтр списка записей сужает выдачу по типу встречи | O5. Встречи всех типов лежат в одном списке; фильтр оставляет только свои, сброс возвращает остальные |
| Отмена встречи владельцем возвращает слот в сетку | O6. Слот становится `busy` после брони и снова `free` после отмены |

Основной сценарий бронирования — первый в таблице; остальные покрывают правила,
которые из него не видны. Коды G/O — идентификаторы сценариев из
[scenarios.md](../scenarios.md). Ветки, до которых из интерфейса не дотянуться
(время не по сетке, момент за границей окна записи), живут в тестах бэкенда.

## Селекторы

Тесты держатся за роли, метки полей и `data-testid`, а не за классы Mantine:
перекраска интерфейса не должна ломать проверки. Две тонкости календаря, на
которые тесты опираются явно:

- дни вне окна записи приходят с `isBookable: false` и рендерятся как `disabled`;
- дни соседнего месяца остаются в разметке скрытыми (`data-hidden`), поэтому из
  выборки кликабельных дней их приходится исключать отдельно.

Сценарии меняют общий календарь владельца, поэтому идут строго по одному
(`workers: 1`), а проверки написаны так, чтобы не зависеть от порядка запуска.
