# Пользовательские сценарии для проверки

Зафиксированный список того, что приложение обязано уметь. Каждый сценарий —
приёмочный критерий: пока он не проходит, задача не закрыта.

Сценарии выражены в терминах пользователя, а не эндпоинтов: соответствие
«сценарий задания → эндпоинт контракта» лежит отдельно, в [coverage.md](coverage.md),
доменные правила — в [domain.md](domain.md).

## Уровни проверки

| Уровень | Чем гоняется | Что проверяет |
|---|---|---|
| Интеграционный, браузер | `e2e/` — Playwright по собранному приложению | Путь пользователя целиком: фронтенд + бэкенд + контракт |
| Интеграционный, API | `backend/test/api.test.ts` — приложение Fastify на базе в памяти | Поведение эндпоинтов и коды ошибок контракта |
| Модульный | `backend/test/slots.test.ts` | Сетка слотов и окно записи в отрыве от HTTP |

Браузерные сценарии — основной способ проверки. API-тесты добирают ветки ошибок,
до которых из интерфейса не дотянуться: время не по сетке, момент за границей
окна записи, невалидный payload.

## Сценарии гостя

Гость работает анонимно: ни на одном шаге не создаётся аккаунт и не требуется вход.

### G1. Запись на встречу от лендинга до подтверждения

Основной сценарий приложения.

1. Гость открывает лендинг и жмёт «Записаться на встречу».
2. В каталоге видит, чей это календарь, и карточки типов встреч с названием,
   описанием и длительностью.
3. Выбирает тип встречи — открывается страница бронирования.
4. В календаре выбирает день из окна записи.
5. В сетке дня выбирает свободное время.
6. Вводит имя, email и, при желании, заметки; подтверждает запись.

**Ожидается:** открывается экран подтверждения по собственному адресу; детали
встречи совпадают с введёнными; время окончания посчитано из длительности типа
события; встреча появляется в списке записей владельца.

**Проверяется:** `e2e/tests/booking.spec.ts` — «гость проходит бронирование от
лендинга до подтверждения».

### G2. Возврат к подтверждению по ссылке

Гость сохраняет адрес экрана подтверждения и открывает его позже.

**Ожидается:** страница открывается с теми же деталями встречи, вход не требуется.

**Проверяется:** `e2e/tests/booking.spec.ts` — «подтверждение открывается повторно
по прямой ссылке».

### G3. Занятое время не предлагается

Гость открывает день, в котором уже есть встреча — в том числе встреча **другого**
типа события.

**Ожидается:** перекрытое время помечено занятым и недоступно для выбора;
остальное время дня доступно; занятый интервал не раскрывает имя и почту того,
кто его занял.

**Проверяется:** `e2e/tests/booking.spec.ts` — «занятое время закрывается и для
другого типа встречи».

### G4. Некорректные данные гостя не уходят на сервер

Гость доходит до формы и отправляет пустое имя и адрес без домена.

**Ожидается:** ошибки показаны у полей, запрос не отправлен, гость остаётся в форме.

**Проверяется:** `e2e/tests/booking.spec.ts` — «форма не отправляет некорректные
данные гостя»; ветка сервера — `api.test.ts`, «невалидные данные гостя — 422
invalid_payload».

### G5. Слот заняли, пока гость заполнял форму

Между выбором времени и отправкой формы это же время бронирует кто-то другой.

**Ожидается:** бронь не создаётся; гость остаётся на странице выбора, видит
сообщение «Это время уже заняли» с объяснением, что произошло, и обновлённую
сетку, где это время помечено занятым. Календарь остаётся согласованным.

**Проверяется:** `e2e/tests/booking.spec.ts` — «слот, занятый во время заполнения
формы, не бронируется»: конкурирующая бронь создаётся запросом, пока форма
открыта в браузере. Ответ сервера — `api.test.ts`, «на занятое время отвечает 409
slot_taken (I1)».

## Сценарии владельца

Авторизации нет: админка открыта по прямому адресу и работает от имени
единственного владельца календаря.

### O1. Публикация нового типа встречи

Владелец создаёт тип встречи: идентификатор, название, описание, длительность.

**Ожидается:** тип появляется в его списке и сразу доступен гостю в публичном
каталоге по адресу `/book/{id}`; в карточке видна заданная длительность.

**Проверяется:** `e2e/tests/admin.spec.ts` — «новый тип встречи появляется в
публичном каталоге».

### O2. Правка типа встречи

Владелец меняет название, описание или длительность существующего типа.
Идентификатор после создания неизменяем.

**Ожидается:** изменения видны гостю в каталоге и на странице бронирования;
новая длительность задаёт новый шаг сетки слотов.

**Проверяется:** `e2e/tests/admin.spec.ts` — «правка типа встречи видна гостю»;
частичное обновление полей — `api.test.ts`, «обновляет только переданные поля».

### O3. Удаление типа встречи

Владелец удаляет тип встречи, на который уже есть запись.

**Ожидается:** тип пропадает из каталога и админки; уже созданная встреча
остаётся в списке записей и сохраняет название типа.

**Проверяется:** `backend/test/api.test.ts` — «удаляет тип события» и «сохраняет
название типа события после его удаления».

### O4. Список предстоящих встреч

Владелец открывает список записей.

**Ожидается:** встречи всех типов в одном списке, по возрастанию времени, с
гостем и заметками; прошедшие встречи по умолчанию не показываются.

**Проверяется:** `backend/test/api.test.ts` — «отдаёт предстоящие встречи по
возрастанию start» и «прошедшая встреча не попадает в список по умолчанию».

### O5. Фильтр списка записей

Владелец сужает список по типу события и по датам, затем сбрасывает фильтры.

**Ожидается:** в списке остаются только подходящие встречи; сброс возвращает
полный список.

**Проверяется:** `e2e/tests/admin.spec.ts` — «фильтр списка записей сужает выдачу
по типу встречи»; границы дат — `api.test.ts`, «фильтрует по типу события и датам».

### O6. Отмена встречи

Владелец отменяет встречу из списка записей.

**Ожидается:** встреча пропадает из списка, освободившееся время снова доступно
гостю для записи.

**Проверяется:** `e2e/tests/admin.spec.ts` — «отмена встречи владельцем возвращает
слот в сетку».

## Правила календаря

Инварианты из [CLAUDE.md](CLAUDE.md), которые не видны из отдельного сценария и
проверяются адресно.

| | Правило | Проверяется |
|---|---|---|
| I1 | Брони не пересекаются по времени, даже у разных типов событий | G3, O6; `slots.test.ts` — «занятость (I1)» |
| I2 | Окно записи — 14 дней от текущего момента | `api.test.ts` — «календарь покрывает окно записи целиком», «время за границей окна», «время в прошлом»; `slots.test.ts` — «окно записи (I2)» |
| I3 | Длительность брони равна `durationMinutes`, `end` считает сервер | G1; `api.test.ts` — «считает end сам из длительности типа события (I3)» |
| I4 | Сетка строится от начала рабочего дня с шагом длительности | O2; `api.test.ts` — «сетка дня отдаётся в шаге типа события», «время не на сетке типа события»; `slots.test.ts` — «сетка рабочего дня (I4)» |
| I5 | Занятый слот не раскрывает данные гостя | G3; `api.test.ts` — «занятый слот не раскрывает гостя (I5)» |

## Как прогнать

```bash
cd backend && npm ci && npm run build && npm test    # API и модульные тесты
cd e2e     && npm ci && npx playwright install chromium
           npm run build:app && npm test             # браузерные сценарии
```

Те же прогоны идут в CI на каждый push и pull request —
[.github/workflows/ci.yml](.github/workflows/ci.yml).
